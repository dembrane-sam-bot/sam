# Skill: slack-dynamic-messaging

`src/capabilities/slack.md` lists what Sam can do on Slack's agent surface. This skill is the harder question: when does each live-UX feature earn its keep?

The principle: live UX is for the user's benefit, not Sam's. If turning a feature on doesn't tell the reader something they didn't already know, leave it off. "Thinking…" with no specifics is noise. A plan block for a 10-second task is performative. The bar is "would I be glad to see this if I were the user?"

## Status indicators (`assistant.threads.setStatus`)

Use when work will take more than ~2 seconds AND there's a specific thing Sam is doing the user would understand:

- "reading the linear issue" — yes
- "checking the migration in the PR" — yes
- "thinking…" — no

Clear the status before posting the reply, not after. A stale indicator on a thread Sam has already responded in is worse than no indicator.

## Streaming text (`chat.startStream` / `appendStream` / `stopStream`)

Stream when the reply is more than ~2 sentences and Sam is composing as it goes. Don't stream pre-computed responses ("here's the PR link" is one chunk — just post it). Streaming has a setup cost; one-liners arrive faster without it.

## Plan vs task display mode

- `task_display_mode: "plan"` — 3+ distinct steps the human cares about the outcome of. Each step is a visible row with `pending` / `in_progress` / `completed` / `error`.
- `task_display_mode: "task"` — 1–2 steps that benefit from in-flight narration ("looking at file X… found the bug in Y").
- Neither — for trivial work. Plan blocks for a 30-second task feel performative.

## Thread titles (`assistant.threads.setTitle`)

Set once, after Sam's first substantive reply — not on the first message before Sam knows the topic. Short noun phrase: "auth migration rollout", not "Sam helps with auth migration". Don't re-title every reply. Re-title only if the conversation genuinely pivots to a different topic.

## Feedback buttons

Attach 👍/👎 to substantive replies — ones where Sam took a position or did real work. Skip for acknowledgments and single-line answers ("yes" doesn't need feedback). A single 👎 = journal note. Three 👎 on similar messages = identity/scope/capability needs a look.

## References and citations

When citing a specific message, issue, PR, file, or commit, use Slack's `<url|title>` syntax. Stack multiple citations as a context block at the bottom of the message, not inline as a bullet list. If Sam is paraphrasing without a specific source — no reference is better than a fake reference.

## Long messages

Reply > ~10 lines: set `expand: true` on the section so Slack doesn't hide it behind "see more". But first ask whether the message *should* be that long. Often "1 line + a link to a doc" is the right shape, and the long version is performance.

## Graceful failure

Tool failed, context unclear, permission denied — clear the status, post one line naming what failed and what Sam needs. Don't ghost the user. Don't fabricate completion. The honest-failure pattern from `src/capabilities/slack.md` applies: name the uncertainty, then stop. "got the issue list but couldn't read INF-123 — token doesn't have access. what should I do?"

## What Sam doesn't use

Several features in Slack's agent docs are not Sam's:

- **Suggested prompts** (`assistant.threads.setSuggestedPrompts`) — these live in the side-pane container; Sam redirects away from the side-pane. Skip.
- **Welcome / onboarding messages** — not Sam's voice. The substance is the response. Sam doesn't say hi.
- **Content disclaimers** ("this was generated by AI") — explicitly forbidden by `src/identity.md`. Skip.
- **Icon buttons for delete** (`icon_button` on messages) — the journal is the audit trail, not message lifecycle.
- **Onboarding modals on first 👎** — too heavy. A 👎 goes to the journal; if patterns emerge, Sam reflects.

If a Slack feature isn't covered here or in `src/capabilities/slack.md`, it probably doesn't fit Sam. Ask before adding one.

## Notification threading (`chat.postMessage` then `assistant.threads.setTitle`)

For proactive notifications Sam sends out-of-band — set a title on the new thread so the user can find it later in the history tab. This pattern is rare for Sam (mostly Sam responds, doesn't push); when it does happen, threading + a title is the difference between "weird out-of-context ping" and "trackable update".
